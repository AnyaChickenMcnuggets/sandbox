# 0005 — Матрица "роль — права" хранится в БД и редактируется админом

- Status: Accepted (уточняет ADR 0003: роли остались фиксированным enum, но что роль может —
  больше не зашито в код)
- Date: 2026-10-07

## Context

ADR 0003 зашил доступ жёстко: `SecurityConfig` проверял `hasRole("ADMIN")`/`hasAnyRole(...)`.
Любая правка "OPERATOR теперь тоже может удалять сценарии" требовала изменения кода и деплоя.
Запрос: админ сам управляет тем, что может каждая роль.

Рассматривались:

1. **Динамические роли** (таблица `role`, создавай сколько угодно) — отвергнуто: `app_user.role`
   (enum + CHECK), `AuthenticationRoles`, JWT-клейм и весь UI привязаны к трём ролям; динамические
   роли — миграция модели без явной потребности (не просили). Роли остаются `ADMIN/OPERATOR/VIEWER`.
2. **`@PreAuthorize("hasPermission(...)")` по контроллерам** — отвергнуто по той же причине, что в
   ADR 0003: политика расползается по файлам.
3. **Права как GrantedAuthority в токене** (`PERM_*` кладёт `JwtAuthenticationFilter`) — отвергнуто:
   права "зашиваются" в выданный JWT на 15 минут, и отзыв права у роли не действует до его
   истечения; плюс `JwtAuthenticationFilter` — `Filter`-бин, и его новая зависимость ломает
   каждый `@WebMvcTest`-слайс.

## Decision

- `Permission` — закрытый enum в коде, каждое право привязано к конкретным эндпоинтам в
  `SecurityConfig` ("эндпоинт -> право"). Новое право через API завести нельзя: право без
  привязки ничего не защищает.
- Матрица `role_permission(role, permission)` в БД (миграция `V12`, засеяна копией прежней жёсткой
  матрицы — поведение при выкатке не меняется). Админ правит через `RolePermissionController`.
- Авторизация спрашивает `RolePermissionService` на КАЖДЫЙ запрос (через
  `PermissionAuthorization` — `AuthorizationManager`, не `Filter`), поэтому изменение матрицы
  действует немедленно, а не после перевыпуска токена. Кэш в памяти процесса, сбрасывается
  ПОСЛЕ коммита (`TransactionSynchronization.afterCommit`), чтобы параллельный запрос не закэшировал
  незакоммиченное старое состояние.
- **`ADMIN` всегда имеет все права и не редактируется** (`PUT .../roles/ADMIN/permissions` → `400`,
  строк для ADMIN в БД нет). Иначе опечатка админа (снять `ROLE_MANAGE` у единственной роли, которая
  им владеет) — безвозвратная блокировка системы.
- Всё под `/api/v1/scenarios|runs|orchestrator|admin`, не сопоставленное праву, — `denyAll()`:
  новый эндпоинт без явной привязки закрыт, а не "просто аутентифицирован".
- `/api/v1/auth/me` возвращает `permissions`; UI-гейтинг — по правам, не по имени роли.
- Смена собственного пароля (`POST /api/v1/auth/change-password`) — не право: любая
  аутентифицированная роль, требует текущий пароль, отзывает все refresh-токены.

## Consequences

- **Кэш локален процессу.** При нескольких инстансах сервиса изменение матрицы на одном не дойдёт до
  остальных без рестарта/общего механизма инвалидации (pub/sub, короткий TTL). Сейчас сервис
  односерверный; при масштабировании — первым делом решить это.
- Удаление значения из `Permission` ломает чтение строк с этим значением (Hibernate не
  десериализует неизвестный enum) — убирая право, сначала миграцией удалить его строки.
- Новый эндпоинт = новая привязка в `SecurityConfig` (иначе `denyAll`) + при необходимости новое
  значение `Permission` + строки в `role_permission` для ролей, которым его надо выдать (новое право
  по умолчанию есть только у ADMIN).
- `SecurityConfigAuthorizationTest` теперь подменяет `RolePermissionService` и проверяет не только
  дефолтную матрицу, но и то, что смена прав действует немедленно.
