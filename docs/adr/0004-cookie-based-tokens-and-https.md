# 0004 — Токены в HttpOnly-куках вместо тела ответа, HTTPS обязателен

- Status: Accepted
- Date: 2026-10-01

## Context

ADR 0003 выдавал `accessToken`/`refreshToken` в JSON-теле `/api/v1/auth/login`/`/refresh`,
оставляя фронтенду решать, где их хранить. На практике это означало `localStorage` — JS-читаемое
хранилище: любой скрипт на странице (в том числе внедрённый через XSS) может прочитать токен и
выдать себя за пользователя, а пользователь/расширение браузера может токен отредактировать —
отредактированный JWT просто не пройдёт проверку подписи (`JwtService.parse` вернёт `null`), но
сам факт, что токен лежит в месте, откуда его можно скопировать/стереть/подменить произвольным
кодом на странице, — реальная поверхность атаки, которой не должно быть у секрета авторизации.

## Decision

**Токены передаются только через `Set-Cookie` (`HttpOnly`), никогда в теле JSON-ответа.**
`HttpOnly` делает куку недоступной для `document.cookie`/любого JS на странице — XSS больше не
может её прочитать. `AuthCookies` (`auth/web`) — единственное место, которое строит/читает эти
куки; `TokenResponse` больше не содержит сырых токенов, только `expiresInSeconds` (не секрет,
фронту полезно для проактивного `/refresh`).

- `access_token` — `Path=/` (нужен на каждый защищённый запрос), TTL = `auth.jwt.access-token-ttl`.
- `refresh_token` — `Path=/api/v1/auth` (нужен только `/refresh`/`/logout`, не должен улетать с
  каждым обычным API-запросом — сужаем поверхность), TTL = `auth.jwt.refresh-token-ttl`.
- Обе — `Secure` (требует HTTPS, см. ниже) и `SameSite=Strict`.
- `/api/v1/auth/refresh`/`/logout` теперь читают refresh-токен из куки, не из тела запроса — у
  фронта просто нет сырого значения, чтобы положить его в body.
- `JwtAuthenticationFilter` сначала ищет `access_token` в куке, и только если её нет — в
  `Authorization: Bearer` (fallback для curl/скриптов/WireMock-тестов, см. `TESTING.md`). Два пути
  не ослабляют друг друга: заголовок не уязвим к CSRF (его не приложить без JS на том же origin —
  это уже XSS, другая угроза), так что его присутствие не меняет модель угроз куки.

**CSRF-токены (double-submit/synchronizer) сознательно не добавлены.** `SameSite=Strict`
останавливает отправку куки на любой cross-site запрос (форма, `fetch`, навигация) — для API,
который не является страницей для прямой навигации, этого достаточно по современным рекомендациям
браузерной безопасности. Если когда-нибудь понадобится `SameSite=None` (кросс-origin фронт, см.
ниже) — это условие теряет силу, и CSRF-защиту нужно будет вернуть первым делом.

**HTTPS обязателен для прода/стейджинга**, не рекомендация. `Secure`-куку браузер не отправит
обратно по обычному `http://` — без HTTPS логин технически пройдёт, но все последующие запросы
будут приходить неаутентифицированными, и это не сразу очевидная ошибка (куки тихо не долетают,
не 400/401 на попытке их поставить). `auth.cookies.secure=false` — исключительно для локальной
разработки (`AUTH_COOKIES_SECURE=false`), не для прода. Как включить HTTPS — `HTTPS_SETUP.md`
(два варианта: TLS на реверс-прокси — рекомендуется, или напрямую в Spring Boot через
`server.ssl.*`); конкретный сертификат/домен — вне зоны ответственности этого решения, инфраструктурно
специфично для окружения разворачивания.

**Фронт и бэкенд должны быть на одном origin.** `SameSite=Strict` не пропускает куку на cross-site
запрос ни при каких обстоятельствах — другой порт/поддомен тоже считается другим origin. Если
архитектурно нужен раздельный origin — это отдельное решение (`SameSite=None` + CORS +
`credentials`), с собственным CSRF-компромиссом, не покрытым этим ADR.

## Consequences

- `TokenResponse` — breaking change API: больше не содержит `accessToken`/`refreshToken`.
  `RefreshRequest` DTO удалён — `/refresh`/`/logout` не принимают тело.
- Фронтенду нечего "хранить" — браузер сам прикладывает куку к каждому запросу на тот же origin;
  инструкция для фронта обновлена (см. `FRONTEND_INTEGRATION.md`).
- Деплой без HTTPS (локальная разработка) требует явного `AUTH_COOKIES_SECURE=false`.
- Новый класс `AuthCookies` — единственный владелец построения/чтения/очистки обеих кук; новый
  тест `AuthCookiesTest`, `JwtAuthenticationFilter`/`AuthController` и их тесты обновлены.
