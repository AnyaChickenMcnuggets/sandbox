# 0006 — Никаких неявных таймаутов ожидания: только из конфига шага сценария

- Status: Accepted
- Date: 2026-10-07

## Context

Ожидание шагов ограничивалось глобальными дефолтами из `application.yml`:
`orchestrator.polling.timeout: 30m` (JOB) и `orchestrator.queue-check-polling.timeout: 10m`
(QUEUE_CHECK). Автор сценария о них не знал: шаг падал "по таймауту" на реальных долгих задачах
(робот занят, большой батч), а причина была в скрытой цифре в конфиге деплоя, не в сценарии.
У `QUEUE_CHECK` переопределение `timeoutSeconds` существовало, у `JOB` — нет вовсе.

Альтернатива "оставить дефолт, но задокументировать" отвергнута: скрытый дефолт остаётся
скрытым, пока он в коде/окружении, а не там, где автор описывает сценарий.

## Decision

- Глобального таймаута ожидания нет. `OrchestratorProperties.Polling` содержит только `interval`.
- Таймаут задаётся ТОЛЬКО в конфиге шага: `JOB.config.timeoutSeconds`,
  `QUEUE_CHECK.config.timeoutSeconds`. Не указан (`null`) — шаг ждёт без ограничения по времени.
  `JOB.config.pollIntervalSeconds` добавлен по аналогии с `QUEUE_CHECK` (интервал — не таймаут,
  глобальный дефолт `orchestrator.polling.interval` остаётся).
- `StatusPoller.pollUntilTerminal(..., Duration timeout, Duration interval)` принимает `null` как
  "без лимита" — единственный источник значения вызывающий (`JobStepExecutor`).
- **Не тронуты** `orchestrator.http.connect-timeout/read-timeout` — это таймаут ОДНОГО HTTP-вызова
  (сетевой уровень), а не ожидание шага; явный и видимый в `application.yml`, без него зависший
  сокет повесил бы поток навсегда.

## Consequences

- Шаг без `timeoutSeconds` может ждать бесконечно: `JOB` — пока робот не освободится/задание не
  завершится; `QUEUE_CHECK` — пока ожидание не выполнится. Спасают: досрочный выход `QUEUE_CHECK`
  (ADR/Sprint 27: все отслеживаемые транзакции уже в конечном статусе), предусловие свободных
  роботов (`min-free-robots`) и ручная остановка прогона (`POST /api/v1/runs/{id}/stop`).
  Для CI/ночных запусков, где зависание недопустимо, сценарий ДОЛЖЕН задавать `timeoutSeconds`.
- Существующие сценарии, полагавшиеся на молчаливые 30/10 минут, теперь без лимита — поведение
  меняется только в худшем случае (зависание), не в успешном.
- `timeoutSeconds` — `Long` секунд, минимальная гранулярность 1 с.
