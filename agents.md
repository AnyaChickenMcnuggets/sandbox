# Guide for future development (agents.md)

Правила для тех, кто (человек или агент) продолжает разработку этого сервиса.

## Структура пакетов

```
com.rpatest
├── auth/{domain,repository,service,web,config}  # свои пользователи/роли/JWT (не оркестратор)
├── orchestrator/{auth,client,dto,exception}      # интеграция с Primo RPA Orchestrator
├── scenario/{domain,repository,service,web}      # CRUD сценариев (наша БД)
├── execution/{domain,engine,repository,web}      # запуск сценариев, статусы, cleanup
└── config/                                       # инфраструктурная конфигурация
```

Правило: `orchestrator/*` не знает про `scenario`/`execution` (только HTTP-интеграция).
`scenario`/`execution` не делают прямых HTTP-вызовов — только через `*Port`-интерфейсы из
`orchestrator`. `auth/*` — аутентификация НАШЕГО API, не путать с `orchestrator/auth` (это логин
В оркестратор, `TokenProvider`/`OrchestratorAuthService` — обслуживает исходящие HTTP-вызовы,
никак не связан с тем, кто вызывает наш собственный API). См. "Аутентификация и роли" ниже.

## ADR (Architecture Decision Records)

`docs/adr/NNNN-краткое-название.md`, нумерация сквозная (следующий свободный номер), не
редактируются задним числом (если решение отменено — новый ADR со Status "Superseded by NNNN",
старый остаётся как есть). Формат: Status/Date, Context (какая проблема, какие альтернативы
рассматривались и почему отклонены), Decision, Consequences.

**Не для каждого изменения.** ADR пишется только когда решение содержит реальный trade-off или
отклонённую альтернативу, которую будущий человек/агент иначе переизобретёт и снова отклонит —
не для рутинного рефакторинга/фичи, у которых и так есть запись в `roadmap.md`. Признак "стоит ли
писать ADR": если через полгода кто-то спросит "а почему не сделали просто X" — ADR должен уже
содержать ответ.

Примеры: `docs/adr/0001-canonical-helper-for-duplicated-cross-cutting-logic.md` (почему дублирующаяся
кросс-cutting логика выносится в один канонический модуль, а не чинится в каждой копии отдельно),
`docs/adr/0002-split-orchestrator-lookup-and-narration.md` (почему id-резолвинг и текстовое
форматирование — два модуля, а не один), `docs/adr/0003-own-api-authentication-jwt-rbac.md`
(механизм аутентификации/роли/провижининг пользователей нашего API),
`docs/adr/0004-cookie-based-tokens-and-https.md` (почему токены — в `HttpOnly`-куках, а не в теле
ответа, и почему это делает HTTPS обязательным в проде),
`docs/adr/0005-editable-role-permission-matrix.md` (права ролей в БД, редактируются админом),
`docs/adr/0006-no-implicit-timeouts.md` (таймауты ожидания — только из конфига шага),
`docs/adr/0007-run-report-snapshot-and-server-side-svg.md` (отчёт — снимок при завершении, Sankey серверным SVG).

## Аутентификация и роли

См. ADR 0003 (`docs/adr/0003-own-api-authentication-jwt-rbac.md`) для полного обоснования; здесь —
что должен знать любой, кто трогает эту область.

- **JWT stateless, не сессия.** Access-токен (HS256, 15 минут, `JwtService`) подписывается и
  проверяется нашим же сервисом — не хранится в БД, валиден по подписи. Refresh-токен (7 дней) —
  НЕ JWT, непрозрачный случайный токен, в БД (`refresh_token`) хранится только его SHA-256 хэш
  (`RefreshTokenService`), с ротацией на каждое обновление (старый отзывается, выдаётся новый).
  Не путайте это с `orchestrator.auth.*` (`TokenProvider`, `JwtExpiryReader`) — та часть логинится
  В оркестратор для исходящих вызовов и просто читает `exp` из ЧУЖОГО токена без проверки подписи;
  здесь — свой токен, свой ключ, обязательна проверка подписи при разборе (`JwtService.parse`).
- **Токены — только в `HttpOnly`-куках, никогда в теле JSON-ответа.** (ADR 0004.) `AuthCookies`
  (`auth/web`) — единственный владелец построения/чтения/очистки обеих кук
  (`access_token`/`refresh_token`); `TokenResponse` токенов не содержит. Если добавляете новый
  способ выдать/вернуть токен — зовите `AuthCookies`, не кладите сырое значение в JSON — это тот же
  класс дыры, ради которой этот ADR и появился (значение, читаемое/редактируемое произвольным JS на
  странице). `JwtAuthenticationFilter` сначала смотрит куку, потом (fallback) `Authorization:
  Bearer` — второе нужно для curl/скриптов/тестов, не для браузера.
  **HTTPS обязателен в проде/стейджинге** — `Secure`-куку браузер не отправит назад по `http://`.
  Как включить — `HTTPS_SETUP.md`. Локально без TLS — `AUTH_COOKIES_SECURE=false`
  (`auth.cookies.secure`), никогда не в проде. CSRF-защита (токены double-submit) сознательно не
  добавлена — опора на `SameSite=Strict`; если когда-нибудь понадобится `SameSite=None`
  (кросс-origin фронт), CSRF-защиту обязательно вернуть первым делом (см. ADR 0004).
- **Эндпоинт -> право — только в `SecurityConfig.securityFilterChain`, не `@PreAuthorize` по
  контроллерам; роль -> права — только в БД (`RolePermissionService`), не в коде.** (ADR 0005.)
  Новый эндпоинт: (1) добавьте значение в `Permission`, если подходящего нет; (2) впишите матчер
  `.access(permissions.has(Permission.X))` в `SecurityConfig` ДО итоговых `denyAll()` (всё под
  `/api/v1/scenarios|runs|orchestrator|admin`, не сопоставленное праву, закрыто — не "просто
  аутентифицирован"); (3) если право надо выдать не только ADMIN — миграция со строками в
  `role_permission` (новое право по умолчанию есть только у ADMIN). Не пишите `hasRole(...)` для
  доступа к функциональности — роль не определяет доступ, право определяет. Три роли
  (`ADMIN`/`OPERATOR`/`VIEWER`, одна на пользователя — enum на `AppUser`, не M:N, не динамические).
  `ADMIN` всегда имеет все права и не редактируется (`PUT .../roles/ADMIN/permissions` → `400`) —
  не "чините" это, это защита от самоблокировки. Кэш `RolePermissionService` локален процессу и
  сбрасывается после коммита; при нескольких инстансах нужна общая инвалидация (ADR 0005).
- **Смена собственного пароля — `POST /api/v1/auth/change-password`**, любая аутентифицированная
  роль, право не нужно; требует текущий пароль, отзывает все refresh-токены, выдаёт новую пару кук.
  Админский сброс (`PUT /api/v1/admin/users/{id}/password`) — отдельный путь без текущего пароля.
- **Никаких неявных таймаутов ожидания** (ADR 0006). Глобальных `*.timeout` для ожидания шагов в
  `application.yml`/`OrchestratorProperties` нет и добавлять не надо: таймаут — только
  `config.timeoutSeconds` шага сценария (`JOB`, `QUEUE_CHECK`), не указан — `null` = ждать без
  лимита. Новый ожидающий/поллящий шаг обязан принимать таймаут из конфига шага и трактовать `null`
  как "без лимита". Сетевые `orchestrator.http.*-timeout` (один HTTP-вызов) — другое, они остаются.
- **Пользователи — только через `AdminUserController` (`ADMIN`-only), self-registration нет.**
  Первый `ADMIN` заводится `AdminBootstrapRunner` при старте, если `app_user` пуста
  (`auth.bootstrap-admin.*` в конфиге) — не Flyway-миграцией (реальный пароль не должен становиться
  содержимым репозитория). Деактивация (`setEnabled(false)`) — мягкая, не удаление (тот же принцип,
  что `agents.md` требует для истории `scenario`/`step` — см. "Денормализуйте на \*Run..." выше):
  удаление осиротило бы `ScenarioRun.triggeredBy`. Деактивация и сброс пароля обязаны отзывать все
  активные refresh-токены пользователя (`RefreshTokenService.revokeAllForUser`) — иначе отключение
  блокирует только будущий логин, а уже выданные токены продолжают работать.
- **`ScenarioRun.triggeredBy` — из `Authentication`, никогда из тела запроса.**
  `RunController.run()` берёт `SecurityContextHolder.getContext().getAuthentication().getName()`;
  `RunRequest` больше не принимает `triggeredBy` от клиента. Если добавляете новый эндпоинт,
  которому нужно знать "кто вызвал" — тот же принцип, не доверяйте значению из тела запроса.
  **Берите `Authentication` из `SecurityContextHolder.getContext()` внутри метода, не как параметр
  контроллера (`Authentication authentication` в сигнатуре).** Параметр резолвится через
  `HttpServletRequest.getUserPrincipal()`, который заполняет сам фильтр-чейн Spring Security — в
  `@WebMvcTest` с `@AutoConfigureMockMvc(addFilters = false)` (стандартный паттерн для
  `*ControllerTest` в этом проекте, см. ниже) фильтры не выполняются, и параметр приходит `null`
  даже с `@WithMockUser`, хотя `SecurityContextHolder` при этом НЕ пуст (`@WithMockUser` заполняет
  его напрямую, независимо от фильтров). `GET /api/v1/auth/me` (`AuthController.me()`) — образец,
  напоролись на это при его добавлении (Sprint 28).
- **Эндпоинт "кто я" (`/me`-подобный) — доступен любой аутентифицированной роли, не размечайте его
  под конкретную роль в матрице `SecurityConfig`.** Узнать свою роль — не операция, требующая
  конкретных прав; он просто должен требовать аутентификации вообще (`anyRequest().authenticated()`
  уже этого достаточно — отдельный матчер под него не нужен, если путь не попадает под более
  специфичные правила выше).
- **`@WebMvcTest`-слайс обязан мокать и `JwtService`, и `AuthCookies`.** `JwtAuthenticationFilter` —
  `@Component`, реализующий `Filter`, поэтому автоматически попадает в любой `@WebMvcTest`-слайс
  независимо от `@AutoConfigureMockMvc(addFilters = false)` (тот отключает РЕГИСТРАЦИЮ фильтра в
  MockMvc, но не исключает сам бин из контекста) — его конструктору нужны оба, без `@MockBean` на
  каждый контекст не поднимется (`UnsatisfiedDependencyException`). Матрица доступа тестируется
  отдельно, одним файлом (`SecurityConfigAuthorizationTest`, реальный `SecurityConfig`,
  `@WithMockUser` с разными ролями, фильтры НЕ отключены) — остальные `*ControllerTest` тестируют
  только HTTP-маппинг/сериализацию с `addFilters = false`, не матрицу доступа. Слайсы, куда входит
  `AuthController`, мокают ещё и `RolePermissionService` (`/me` отдаёт права); в
  `SecurityConfigAuthorizationTest` он подменён моком с дефолтной матрицей, тесты меняют её на лету.

## Как добавить новый эндпоинт оркестратора

**Важно:** swagger содержит и неактуальные/неиспользуемые эндпоинты — их там просто оставили.
Совпадение пути и схемы в swagger НЕ гарантирует, что эндпоинт реально работает на стенде
(пример: создание/получение задания реально работает только через `/api/Assignments/v2`,
`/api/Assignments` без версии в ответе на POST даёт 400). Ещё коварнее случай, когда неактуальный
эндпоинт не падает с ошибкой, а тихо отдаёт `200` в чужом формате ответа: `GET
/api/ExchangeQueues/{id}/Items` (без версии) возвращал бы `{totalCount, items}` (`PageDto`), но
реально работает только `v2` с форматом `{totalCount, filterCount, result}` (`ListResultDto`) —
без внешнего подтверждения десериализация просто тихо возвращала бы пустой список вместо ошибки,
и шаг `QUEUE_CHECK` завис бы в поллинге до таймаута вместо явного падения. Перед тем как
завязываться на новый эндпоинт по одному только swagger — **спроси пользователя**, рабочий ли это
метод, или нужно искать другой; у него есть подтверждённо рабочие примеры вызовов —
[OrcService.java](OrcService.java) (Java/Spring) и [orc_worker.py](orc_worker.py) (Python) — сверяйся
с ними, а не только со swagger, особенно для форматов ОТВЕТОВ (не только путей запросов).

1. Найти операцию в [orc_swagger.json](orc_swagger.json) (`paths./api/...`), выписать
   requestBody/response `$ref` на `components.schemas`.
2. Добавить DTO в `orchestrator/dto` — поля 1:1 со схемой (тип, `nullable`), без лишней логики.
3. Добавить метод в соответствующий `*Port`-интерфейс и реализовать в `*Client`
   (`RestClient`, см. `AssignmentsClient` как образец: `.uri(...).header(...).retrieve()`).
4. Обернуть непредвиденные ошибки в `OrchestratorApiException` (сетевые/5xx) — НЕ глотать
   молча.
5. Написать WireMock-тест: застабить `orc_swagger.json`-совместимый ответ, проверить
   маппинг DTO и обработку ошибочных статусов (401/404/500).

## DAG сценария

- `scenario_step_edge(from_step_id, to_step_id)` — рёбра. Корневые шаги — без входящих рёбер.
  Разветвление (fan-out) — несколько исходящих рёбер у одного шага (см. `ScenarioExecutionEngine`)
  — поддерживается и оттестировано.
- **Fan-in (несколько родителей у одного шага) поддерживается.** Движок построен на пулл-модели
  (`ScenarioExecutionEngine.getOrCreateFuture`, Sprint 24): каждый узел вычисляет своё будущее как
  зависимость от будущих своих родителей, а не наоборот (родитель раньше "толкал" детей —
  `executeStepAsync`, теперь такого метода нет). `futuresByStepId` мемоизирует по `stepId`, поэтому
  узел с несколькими входящими рёбрами получает ровно одно будущее и выполняется один раз, только
  когда **все** его родители завершились успешно (`actual` = `SUCCEEDED` у всех, не "хотя бы один"
  — см. запрос пользователя: "выполнять только если все предшествующие блоки... выполнены и
  выполнены успешно"). Если хотя бы один родитель не `SUCCEEDED` (упал или сам не выполнялся) — узел
  не запускается и остаётся `PENDING` навсегда, как и любой другой недостигнутый шаг; это каскадится
  дальше по DAG теми же средствами, без специального кода.
  **Релевантны только родители текущего прогона.** При запуске с `startStepId` (см. ниже) родитель
  вне множества `reachable` (недостижим из точки старта обходом по `outgoing`) не блокирует
  fan-in-узел — он в принципе не существует в этом прогоне, ждать его нечего. Множество `reachable`
  вычисляется один раз в начале `runScenario` (BFS по исходящим рёбрам от корней) и передаётся в
  `getOrCreateFuture` как фильтр для `incoming`.
  Не блокирует поток на `.join()` в ожидании родителей: `.join()` внутри `thenComposeAsync` дергается
  только после `allOf(parentFutures)`, то есть на уже завершённых будущих — то же свойство, ради
  которого чинился дедлок в Sprint 14 (см. ниже), сохранено. Не пишите новый push-код "родитель
  триггерит детей" — при добавлении новой логики инициации шагов используйте тот же пулл-паттерн
  (узел сам собирает зависимости от родителей), иначе fan-in снова сломается.
- **Очереди, которые читает/пишет `JOB`, должны быть его предками в DAG, не потомками** — движок
  не знает, какую очередь использует конкретный проект (это скрыто в Studio), и просто идёт по
  рёбрам в заданном порядке. Ставить выходную очередь как ребёнка задания ("чтобы было куда
  писать") — ошибка: она физически создаётся только когда движок до неё доходит, то есть уже
  *после* того, как заданию она понадобилась. Правильно: все относящиеся к `JOB` `QUEUE`-шаги —
  его предки; проверочные `QUEUE_CHECK`-шаги — его потомки. См. `architecture.md`, раздел
  "Правило проектирования DAG". Для `QUEUE_CHECK` это правило не критично (см. ниже) — он сам
  идемпотентно создаёт отсутствующую очередь и просто ждёт дольше, если порядок перепутан; для
  `JOB` критично всегда, он очередей не создаёт вообще.
- **Никогда не блокируйте поток `scenarioExecutionExecutor` внутри самого себя рекурсивным
  `CompletableFuture.runAsync(...).join()`.** Так было реализовано изначально и привело к реальному
  дедлоку на стенде пользователя: каждый уровень DAG навсегда занимал отдельный поток пула
  в ожидании следующего уровня, а `ThreadPoolExecutor` создаёт потоки сверх `corePoolSize` только
  когда очередь заполнена — на цепочке длиннее `corePoolSize` все core-потоки оказывались
  заблокированы друг на друге раньше, чем пул успевал вырасти до `maxPoolSize` (см. `roadmap.md`,
  Sprint 14). Правильная схема — `supplyAsync(...).thenComposeAsync(...)` (см.
  `ScenarioExecutionEngine.executeStepAsync`): продолжение планируется на пуле по готовности, не
  занимая поток ожиданием. Любая будущая доработка движка (fan-in и т.п.) обязана сохранить это
  свойство — если добавляете новую точку ветвления/ожидания, прогоните регрессионный тест
  `doesNotDeadlockOnLinearChainLongerThanExecutorThreadCount` (реальный ограниченный пул +
  `assertTimeoutPreemptively`) как образец, как это проверять.
- **Запуск с произвольного шага.** `ScenarioExecutionEngine.runScenario(Long runId, Long
  startStepId)` — если `startStepId` задан, обход начинается с этого шага как с единственного
  "корня" для этого прогона, а не с корней DAG сценария. Шаги "до" точки старта по-прежнему
  получают `StepRun(PENDING)` (пре-создаются все разом, как обычно), но обход их не касается — они
  остаются `PENDING` навсегда, как и любой пропущенный из-за упавшего предка шаг (см. выше).
  Валидация "шаг принадлежит сценарию" — на уровне `ExecutionService.startRun`, а не движка;
  движок сам падает `StepExecutionException`, если `startStepId` не нашёлся в `stepsById` (не
  должно происходить, если валидация в сервисе прошла, — защита от рассинхрона). Если добавляете
  новый способ инициировать прогон — сохраняйте этот же принцип: "запуск не с начала" не должен
  требовать пересчёта/специальной обработки остальной топологии, движок просто игнорирует всё, что
  недостижимо из указанной точки старта.
- При создании/редактировании сценария `ScenarioService` обязан проверять отсутствие циклов
  (топологическая сортировка) — не убирайте эту проверку, движок исполнения не рассчитан на циклы.
- Новый тип шага (кроме `JOB`/`QUEUE`/`QUEUE_CHECK`) добавляется как ещё одна реализация
  `StepExecutor` + значение в `ScenarioStepType` + миграция, расширяющая CHECK-constraint
  `scenario_step_type_check` (см. `V4__queue_check_step.sql` как образец), без изменения
  `ScenarioExecutionEngine` — движок обходит DAG независимо от типа шага.
- `QUEUE_CHECK` (`QueueCheckStepExecutor`) — образец "проверочного" шага: сам ничего не должен
  делать в оркестраторе, кроме идемпотентного обеспечения предпосылки (`ExchangeQueueProvisioner`,
  см. ниже), а дальше поллит существующее состояние до совпадения с ожиданием или таймаута.
  Полезный паттерн для любой будущей "проверочной" логики: не встраивать проверку внутрь шага,
  который создаёт сущность (`JobStepExecutor`/`QueueStepExecutor`), а выносить в отдельный шаг
  сразу после него в DAG — так проверка переиспользуема и не завязана на то, что именно её вызвало.
- **Идемпотентность create-операций.** Любая сущность оркестратора с фиксированным (не
  сгенерированным нами) именем, которую сценарий может пересоздавать при повторном прогоне без
  `cleanup` (сейчас — `ExchangeQueue`), должна создаваться через паттерн find-or-create
  (`ExchangeQueueProvisioner.ensureExists` — образец), а не безусловным `POST`. Это не касается
  `Assignment`: он всегда новый и с уникальным именем (`_<runId>_<stepId>`) — намеренно не
  идемпотентен, задание одноразовое по своей природе оркестратора.
- **Владение сущностью для cleanup ≠ факт использования.** `ExchangeQueueProvisioner.ensureExists`
  возвращает `Result(queue, created)` — `created=false`, если очередь просто переиспользована по
  имени. Только `created=true` даёт право удалить сущность на cleanup (`StepRun.
  orchestratorQueueOwned`, выставляется только в `QueueStepExecutor`). `QueueCheckStepExecutor`
  тоже вызывает `ensureExists` (get-or-create, чтобы было что поллить, если DAG собран раньше
  соответствующего `QUEUE`-шага), но **никогда** не помечает владение — он про проверку, а не про
  создание, и не должен получать право стирать чужую очередь на cleanup. При добавлении нового
  шага, который что-то создаёт/переиспользует в оркестраторе — следуйте этому же различию, не
  привязывайте право на удаление к самому факту "у шага есть orchestratorXxxId".
- **`ERROR` не всегда финален.** Оркестратор с настроенным `maxRetray > 0` на очереди сам
  перекладывает транзакцию обратно в очередь после Error для повторной попытки — пока
  `item.retray < queue.maxRetray`, текущий `ERROR` может ещё смениться на `SUCCESS`.
  `QueueCheckStepExecutor.effectiveStatus` учитывает это при подсчёте (`IN_PROGRESS` вместо
  `ERROR`, пока лимит не исчерпан) — если добавляете новую логику, интерпретирующую статус
  транзакции для принятия решений (не для отображения — `QueueAuditService` намеренно показывает
  сырой статус для отладки), учитывайте `retray`/`maxRetray`, а не только `lastEventType`.
- **`QUEUE_CHECK` выходит из поллинга досрочно, если ждать уже нечего.** Если по `naturalKeyFilter`
  (непустому — для "смотрим всю очередь без фильтра" это не применимо, набор не закрыт, новые
  транзакции могут появиться в любой момент) все отслеживаемые транзакции уже в конечном статусе
  (`isAllTerminal` — не `NEW`/`IN_PROGRESS`, в том числе `ERROR`, который оркестратор ещё может
  переложить на повтор — см. `effectiveStatus`) и проверка всё ещё не пройдена — их статус сам по
  себе больше не поменяется, досиживать полный `timeout` бессмысленно. `pollUntilSatisfied` не
  рубит по первому же такому снимку (мог появиться race — новая транзакция с тем же
  ключом/префиксом вот-вот придёт), а падает только если ДВА снимка подряд показывают одно и то же
  (тот же размер набора, всё так же конечное, всё так же недостаточно) — т.е. всегда минимум один
  подтверждающий опрос перед отказом. Если меняете логику поллинга `QUEUE_CHECK` — сохраняйте это
  свойство "одна лишняя попытка, не ноль и не timeout".
- **`expectedStatusCounts` — это порог "не меньше", а не точное равенство.**
  `QueueCheckStepExecutor.satisfies` сравнивает `actual >= expected` по каждому статусу
  (изначально было `actual != expected` — строгое равенство роняло шаг, если фактическое
  количество превысило ожидание, хотя цель проверки автора сценария была уже достигнута). Если
  где-то ещё в движке добавляете сравнение "факт против ожидания счётчика" — тот же принцип по
  умолчанию: не меньше запрошенного, а не ровно столько же, если явно не оговорено иное.
- **Денормализуйте на \*Run то, что должно пережить свой родитель.** История (`ScenarioRun`/
  `StepRun`) не должна становиться нечитаемой из-за того, что описывающий её `TestScenario`/
  `ScenarioStep` был удалён или пересоздан (`PUT /scenarios/{id}` удаляет и заново создаёт ВСЕ
  `scenario_step` сценария на каждое редактирование, не только изменённые). Отсюда: FK от
  `scenario_run`/`step_run` к живым сущностям (`scenario_id`, `step_id`) — `ON DELETE SET NULL`,
  не `CASCADE`; а всё, что нужно для отображения истории (`scenario_name`, `step_name`/
  `step_type`), копируется на сам `*Run` в момент создания (`ExecutionService.startRun`/
  `ScenarioExecutionEngine`), а не вычисляется join'ом на чтении. Если добавляете новое поле в
  `ScenarioResponse`/`StepResponse`, которое хотелось бы также видеть в `RunResponse`/
  `StepRunResponse` — денормализуйте его тем же способом, а не тяните через `scenarioId`/`stepId`
  на фронте: это и лишний запрос, и данные, не переживающие удаление/редактирование родителя. При
  добавлении новой сущности с похожей связью "запись истории → её живое описание" — тот же
  принцип: `ON DELETE SET NULL` + денормализация показываемых полей, а не `CASCADE`.
- **Списки элементов очереди — только через фильтр оркестратора, никогда полным постраничным
  перебором ради поиска конкретных ключей.** `GET /api/ExchangeQueues/v2/{id}/Items` поддерживает
  `NaturalKey`/`NaturalKeyPart` (см. `orc_swagger.json` — не задокументировано ни в
  `OrcService.java`, ни в `orc_worker.py`, легко пропустить, ориентируясь только на эталонные
  клиенты). Перебор всех страниц оправдан только когда действительно нужно посчитать/увидеть
  **всё** содержимое очереди (как в `QUEUE_CHECK` без `naturalKeys`, когда важен только
  `minTotalCount`) — в любом другом случае это не просто неэффективно, а по факту ограничивает
  поиск потолком `MAX_PAGES × PAGE_SIZE`: транзакция дальше этой границы для перебора не
  существует, хотя реально есть в очереди (ровно это и было причиной "иногда не находит
  транзакции, хотя они есть", Sprint 19). Серверную фильтрацию всё равно стоит перепроверять
  собственным точным условием на стороне сервиса — не доверяйте вслепую документированной (тем
  более недокументированной) семантике чужого API. **Канонический хелпер — `QueueItemFinder`**
  (`execution/engine`): любой новый код, которому нужен список/подсчёт элементов очереди, должен
  звать его, а не писать свой постраничный цикл или свою пару "фильтр/без фильтра" — `QueueAuditService`
  (ручной аудит, Sprint 23) и `QueueCheckStepExecutor` уже через него. Если результат должен
  сужаться по умолчанию до того, что конкретному шагу известно (его собственные `transactions`/
  `naturalKeys` из `ScenarioStep.config`) — выводите набор ключей на вызывающей стороне (см.
  `QueueAuditService.deriveFilter`) и передавайте в `QueueItemFinder.find`, сам хелпер про шаги
  ничего не знает.
- **Статусы прогона — только человекочитаемые имена, никогда голый numeric id оркестратора.**
  `detail`/сообщения об ошибках читает человек в процессе прогона (см. "Наблюдаемость выполнения"
  в `architecture.md`) — `"id=1447"` ничего не говорит о том, что происходит. Для `Assignment`
  используйте сгенерированное имя (`assignmentName`, `_<runId>_<stepId>` — оно уже есть, просто
  прокидывайте его в сообщения вместо `assignmentId`), для проекта — `rpaProjectName` из конфига
  либо, если задан только `rpaProjectId`, best-effort резолвинг имени. Raw id никуда не девается из
  ответа API (`orchestratorAssignmentId` и т.п.) — программному клиенту он по-прежнему нужен, но
  текстовые сообщения для человека им не оперируют.
  **Канонические модули — `OrchestratorLookup` и `OrchestratorNarration`** (ADR 0002,
  `docs/adr/0002-split-orchestrator-lookup-and-narration.md`). Любое новое "получить id→имя от
  оркестратора" (проект, и в будущем любая другая сущность) — метод в `OrchestratorLookup`
  (`execution/engine`, единственный владелец `RpaProjectsPort`/`RpaProjectQueuePort` для этой цели);
  неудача резолвинга — best-effort, не должна ронять шаг, это не критичный путь. Любое "превратить
  уже полученные данные в фразу для `StepRun.detail`/ошибки" — метод в `OrchestratorNarration`
  (`orchestrator/util`, чистые статические функции, без I/O — как `OrchestratorNames`). Не пишите
  свой `.map(...).orElse("id=" + id)` или конкатенацию строк статуса в новом коде — это тот же
  паттерн дублирования, ради которого выделен `QueueItemFinder` (см. выше), только для текста, а не
  для чтения очереди.
- **Предусловия запуска проверяются один раз, до создания `ScenarioRun`, а не внутри движка.**
  `ExecutionService.requireEnoughFreeRobots` — образец: простая, дешёвая проверка ("хватит ли
  свободных роботов на оркестраторе") выполняется синхронно в `startRun`, до
  `runRepository.save(...)`, и либо пускает прогон, либо сразу (`409 CONFLICT`) не создаёт вообще
  ничего — никакого "запустили, потом упало через 30 минут по таймауту внутри уже
  зафиксированного прогона". Если понадобится новое предусловие такого рода (не специфичное для
  конкретного шага, а общее "стоит ли вообще начинать") — тот же принцип: fail fast перед созданием
  записи в БД, а не внутри `ScenarioExecutionEngine`/конкретного `StepExecutor`, откуда откатывать
  уже созданный `ScenarioRun` неудобно и не нужно. Не путайте это с проверками внутри `StepExecutor`
  (там уместны специфичные для типа шага предпосылки, например существование проекта) — это разные
  уровни: предусловие рана целиком vs. предусловие конкретного шага.
- **Предусловие, от которого зависит доступность кнопки на фронте — всегда read-only эндпоинт
  рядом, а не только исключение по факту попытки.** `ExecutionService.getRobotAvailability()` — тот
  же самый расчёт, что и `requireEnoughFreeRobots()`, но без побочных эффектов и исключения;
  `OrchestratorController.robotsAvailability()` отдаёт его наружу для поллинга. Не дублируйте
  логику условия между "проверка при запуске" и "снимок для поллинга" — второе должно быть
  реализовано через первое (или наоборот), а не независимым отдельным вычислением: если условия
  разъедутся, фронт будет показывать кнопку разблокированной, а запуск — падать `409`, или
  наоборот. Тот же принцип применим к любому будущему предусловию, которое стоит показывать
  пользователю ДО попытки действия, а не только объяснять постфактум через код ошибки.
- **Реальное завершение `JOB` — не через `AssignmentStatus`.** `GET /api/Assignments/v2/{id}`
  показывает только то, что оркестратор поставил проект в очередь выполнения (`Complete` наступает
  почти сразу после `Start`, задолго до того как робот реально возьмётся за работу). Источник
  истины — `RpaProjectLaunchesPort.getByAssignment` (реальные запуски на роботах,
  `robotStartedAt`/`completedAt`/`success`) и `RpaProjectQueuePort` (пока запись в очереди
  ожидания — робот ещё не подхватил; `errorMsg` там же при сбое). Если добавляете новую логику,
  которой нужно "дождаться, пока задание реально выполнится" — используйте `StatusPoller`, не
  `AssignmentsPort.get()`.

## Отчёт по прогону

См. ADR 0007. Что должен знать тот, кто трогает эту область:

- **Отчёт - снимок на момент завершения прогона** (`run_report`, `RunReportService`), не расчёт
  "на лету": очереди чистятся на `cleanup`, а `PUT /scenarios/{id}` пересоздаёт все шаги и рёбра.
  Строится в `RunCompletionHandler`, который зовёт `ExecutionService` после `engine.runScenario`;
  движок про отчёты не знает - не добавляйте зависимость движка от отчётов.
- **Итог шага для отчёта - `StepRun.setResult(Map)`, а не текст в `detail`.** Новый шаг, который
  должен попасть в отчёт, обязан записать `result` (JSON-безопасные значения) ДО того, как может
  бросить исключение - иначе упавший шаг покажет в отчёте "нет данных". Новый тип шага - ещё и
  секция в `RunReportHtmlRenderer`, иначе он будет виден только в общей таблице шагов.
- **`RunReportSnapshot` - хранимый формат**: поле можно добавлять, нельзя переименовывать/удалять
  (старые строки `run_report` перестанут читаться).
- **Всё, что пришло от пользователей/оркестратора, в HTML экранируется** (`esc`/`HtmlUtils`), в
  отчёте нет скриптов, ответ отдаётся с `Content-Security-Policy: default-src 'none'`. Не добавляйте
  JS и внешние ресурсы в отчёт.
- **Письмо - `ReportNotifier`, по умолчанию выключено** (`report.notification.enabled`), сбой не
  должен влиять на прогон и отчёт (ловится и логируется). Формат `Mail_Body` - в одном месте,
  `ReportMail`.

## Язык логов и логирование запросов

- **Всё, что попадает в терминал/лог — на английском** (`log.*`, текст для `StepProgressReporter`,
  `OrchestratorNarration`, сообщения `StepExecutionException`/`OrchestratorApiException`/
  `OrchestratorAuthException`, которые печатаются в стектрейсах), и **только ASCII**: Windows-консоль
  ломает кириллицу и даже типографские тире (`—`) — пишите `-`. Сообщения, видимые лишь через API
  (`NotFoundException` и т.п.), и комментарии в коде могут быть на русском.
- **Каждый запрос логирует `RequestLoggingFilter`** (`--> ...` на входе, `<-- ... took N ms` на
  выходе, с пользователем и IP). Это НЕ `@Component`: Boot поставил бы такой бин в конец
  servlet-цепочки, после Spring Security, и 401/403 в него бы не попадали. Он создаётся в
  `SecurityConfig` и вставляется `addFilterAfter(.., JwtAuthenticationFilter.class)`. Не логируйте
  там заголовки/куки/тела — токены и пароли.

## Паттерн: live-прогресс и логирование долгих шагов

Любой шаг/поллер, который может выполняться дольше пары секунд (ожидание робота, поллинг очереди),
обязан звать `StepProgressReporter.report(stepRun, "человекочитаемый текст фазы")` на каждом
значимом переходе состояния — не только при входе/выходе из шага, но и на каждой итерации
поллинга, если она меняет наблюдаемые данные (новые счётчики, новый статус робота и т.п.). Один
вызов одновременно (1) обновляет `StepRun.detail`/`detail_updated_at` (видно через `GET
/api/v1/runs/{runId}`) и (2) логирует ту же строку на INFO — не разводите эти два действия
руками в новом коде, `StepProgressReporter` — единственная точка входа. Формулируйте текст фазы
так, чтобы по нему одному было понятно, что происходит прямо сейчас, без похода в код (пример —
`architecture.md`, раздел "Наблюдаемость выполнения"). Не логируйте на INFO конфиденциальные
данные (токен, пароль — см. "Секреты и логирование" ниже); сырые тела HTTP-ответов оркестратора —
не выше DEBUG.

## Миграции Flyway

- Файлы `src/main/resources/db/migration/V{N}__{name}.sql`, только вперёд (не редактировать уже
  примененные `V*`-файлы, добавлять новые).
- Каждая новая сущность/колонка — отдельная миграция, покрытая repository-тестом на
  Testcontainers.

## Секреты и логирование

- Пароль/логин оркестратора — только в `orchestrator.credentials.*` (Jasypt `ENC(...)`),
  никогда в коде/тестах в открытом виде и никогда в БД.
- JWT-токен не логировать и не персистить — только `TokenProvider` в памяти.
- В `logback`/`application.yml` не включать уровень `DEBUG` для `org.springframework.web.client`
  в проде — там могут светиться заголовки авторизации.

## Тесты и покрытие

- Каждый новый `*Client`/`*Port` — WireMock-тест на happy path + минимум один код ошибки.
- Каждый новый `Service`-метод — unit-тест (моки портов/репозиториев) + edge case (не найдено,
  невалидное состояние).
- Каждый новый `Controller`-метод — MockMvc-тест (успех + 4xx).
- Перед PR — `mvn clean verify`, JaCoCo-порог не должен упасть.

## Стиль кода

- SOLID: `*Port`-интерфейсы держат сервисы независимыми от HTTP-деталей (DIP), новый тип шага —
  через `StepExecutor` (OCP), контроллеры/сервисы/клиенты — одна ответственность каждый (SRP).
- Без комментариев "что делает код" — только там, где неочевидна причина (например, почему retry
  не применяется к POST).
- Конфигурируемость — новые интервалы/таймауты/лимиты только через `application.yml` +
  `@ConfigurationProperties`, не хардкодить.
