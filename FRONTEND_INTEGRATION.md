# Инструкция для фронтенда: аутентификация (Sprint 26)

Весь backend API теперь требует аутентификации. До этого спринта каждый эндпоинт был открыт —
теперь нужен вход в систему и токен в каждом запросе. Это ломающее изменение: без доработки
фронтенда все текущие вызовы API начнут получать `401 Unauthorized`.

Полное техническое обоснование — `docs/adr/0003-own-api-authentication-jwt-rbac.md` и раздел
"Аутентификация нашего API" в `architecture.md`. Здесь — только то, что нужно фронтенду.

## 1. Что нужно сделать

1. Экран логина (username + password).
2. Хранение `accessToken`/`refreshToken` (не в куке — сервер их не ставит; sessionStorage/
   localStorage/память приложения — на ваше усмотрение).
3. Добавление `Authorization: Bearer <accessToken>` ко всем запросам к API, кроме `/api/v1/auth/*`
   и `/actuator/health`.
4. Обработка истечения access-токена (15 минут) — автоматический refresh или редирект на логин.
5. Скрытие/дизейблинг элементов UI по роли пользователя (см. раздел 4).
6. Убрать поле "кто запускает" из формы запуска сценария, если оно было — сервер больше не
   принимает его от клиента (см. раздел 5).

## 2. Поток аутентификации

### Логин

```
POST /api/v1/auth/login
Content-Type: application/json

{ "username": "operator1", "password": "..." }
```

Успех — `200`:
```json
{ "accessToken": "eyJ...", "refreshToken": "8f3a...", "expiresInSeconds": 900 }
```

Неверный логин/пароль или отключённый пользователь — `401`:
```json
{ "code": "INVALID_CREDENTIALS", "message": "Неверный логин или пароль", "details": [] }
```
Сообщение намеренно не различает "нет такого пользователя" и "неверный пароль" — не показывайте
пользователю более конкретную подсказку, чем пришла от сервера.

### Использование access-токена

Каждый запрос к API (кроме `/api/v1/auth/*` и `/actuator/health`):
```
Authorization: Bearer eyJ...
```
Живёт 15 минут. Просроченный/невалидный/отсутствующий токен → `401`, недостаточно прав для
конкретного действия (роль есть, но не та) → `403`. Оба варианта — тот же JSON-формат ошибки, что
и остальной API (`ErrorResponse`: `code`/`message`/`details`).

### Обновление токена (refresh)

```
POST /api/v1/auth/refresh
Content-Type: application/json

{ "refreshToken": "8f3a..." }
```
Успех — `200`, новая пара токенов (те же поля, что у login). **Refresh-токен одноразовый** —
после успешного `/refresh` старый становится недействителен, сохраняйте оба новых значения, а не
только `accessToken`. Просроченный/уже использованный/отозванный refresh-токен → `401` — в этом
случае обычный сценарий фронтенда: разлогинить пользователя и показать экран логина заново, не
зацикливать retry.

Рекомендуемая логика: на каждый `401` от API (кроме самого `/auth/login`) — один раз попробовать
`/auth/refresh`, при успехе повторить исходный запрос с новым `accessToken`; при неудаче — разлогин.

### Logout

```
POST /api/v1/auth/logout
Content-Type: application/json

{ "refreshToken": "8f3a..." }
```
`204 No Content`. Отзывает refresh-токен на сервере (access-токен просто выкидывается на клиенте —
серверу отзывать нечего, он живёт максимум 15 минут и так). Зовите при явном выходе пользователя.

## 3. Матрица ролей — что доступно

Три роли, у пользователя ровно одна. Если запрос успешен на бэке, но роли не хватает — `403`, не
`404`/пустой ответ, так что можно (и нужно) заранее скрывать недоступные действия в UI, а не только
ловить ошибку постфактум.

| Действие | VIEWER | OPERATOR | ADMIN |
|---|:---:|:---:|:---:|
| Смотреть список/детали сценариев | ✅ | ✅ | ✅ |
| Смотреть статус прогона, элементы очереди, доступность роботов | ✅ | ✅ | ✅ |
| Создать/отредактировать сценарий | ❌ | ✅ | ✅ |
| Запустить/остановить прогон, cleanup | ❌ | ✅ | ✅ |
| Удалить сценарий | ❌ | ❌ | ✅ |
| Управление пользователями (`/api/v1/admin/users/*`) | ❌ | ❌ | ✅ |

`VIEWER` — режим "только просмотр": прячьте кнопки создания/запуска/удаления целиком, не просто
дизейбльте — так понятнее, что это не баг. `ADMIN`-раздел (управление пользователями) — отдельный
пункт меню, видимый только `ADMIN`.

Роль пользователя не приходит отдельным эндпоинтом — она "внутри" JWT (клейм `role`), но
декодировать токен на фронте ради роли не нужно: **проще всего запомнить роль в момент логина** —
добавьте её в ответ `/auth/login`, если понадобится {{в текущей версии `TokenResponse` роли нет,
только токены — если фронту нужна роль сразу после логина, скажите backend-команде, добавим поле
или отдельный `GET /api/v1/auth/me`}}. Пока самый надёжный способ узнать роль — декодировать
payload JWT на фронте (это не секрет, только подпись секретна) или ловить `403` и адаптироваться.

## 4. Админ-панель: управление пользователями

Все — только с ролью `ADMIN`, все под `/api/v1/admin/users`.

**Создать пользователя**
```
POST /api/v1/admin/users
{ "username": "operator1", "password": "минимум 8 символов", "role": "OPERATOR" }
```
→ `201`, тело — `UserResponse` (см. ниже). Дубликат `username` → `409 CONFLICT`. Короткий пароль
→ `400` (стандартная валидация, `code: "VALIDATION_FAILED"`).

**Список / один пользователь**
```
GET /api/v1/admin/users
GET /api/v1/admin/users/{id}
```
`UserResponse`:
```json
{ "id": 5, "username": "operator1", "role": "OPERATOR", "enabled": true, "createdAt": "2026-09-29T10:00:00+03:00" }
```
Пароля/хэша в ответе никогда нет.

**Сменить роль**
```
PUT /api/v1/admin/users/{id}/role
{ "role": "ADMIN" }
```

**Включить/отключить**
```
PUT /api/v1/admin/users/{id}/enabled
{ "enabled": false }
```
Отключение — не удаление, строка остаётся (аудит). Отключённый пользователь не может залогиниться,
и его уже выданные токены сразу перестают работать (не только будущий логин).

**Сбросить пароль**
```
PUT /api/v1/admin/users/{id}/password
{ "newPassword": "минимум 8 символов" }
```
→ `204`. Удаления пользователя нет — только `enabled: false`.

Первого `ADMIN` фронт не создаёт — он заводится backend'ом при первом старте (см. `TESTING.md`,
раздел "0a. Первый ADMIN и логин"), спросите его логин/пароль у бэкенд-команды/DevOps.

## 5. Breaking change: поле `triggeredBy` убрано из запроса запуска

Раньше:
```
POST /api/v1/scenarios/{id}/run
{ "triggeredBy": "имя_которое_вводил_пользователь", "startStepId": null }
```
Теперь `triggeredBy` в теле запроса **игнорируется/не принимается** — сервер сам берёт имя из
токена аутентификации. Если в форме запуска было поле "от чьего имени запускать" — уберите его,
это больше не нужно и не имеет эффекта. Тело запроса теперь:
```json
{ "startStepId": null }
```
(поле `startStepId` можно вообще не передавать, если запуск с начала — тело необязательно, как и
раньше). В ответе `GET /api/v1/runs/{runId}` поле `triggeredBy`, вероятно, отображается уже сейчас
в UI прогона — оно как было, так и осталось, просто источник значения сменился на "кто реально был
залогинен", а не на то, что ввели в форму.

## 6. Формат ошибок (без изменений, для справки)

Все ошибки API — единый JSON:
```json
{ "code": "STRING_CODE", "message": "человекочитаемый текст", "details": [] }
```
Новые коды, которых раньше не было:

| HTTP | code | Когда |
|---|---|---|
| 401 | `UNAUTHORIZED` | нет токена / просрочен / подделан |
| 401 | `INVALID_CREDENTIALS` | неверный логин/пароль при `/auth/login`; невалидный refresh-токен при `/auth/refresh` |
| 403 | `FORBIDDEN` | токен валиден, но роли не хватает на это действие |
| 409 | `CONFLICT` | (уже было) — теперь также при создании пользователя с занятым `username` |

## 7. Чек-лист интеграции

- [ ] Экран логина, хранение `accessToken`/`refreshToken`
- [ ] `Authorization: Bearer` во все запросы, кроме `/auth/*` и `/actuator/health`
- [ ] Обработка `401` на любом запросе: попытка `/auth/refresh` → повтор запроса, при неудаче — разлогин
- [ ] `logout` реально зовёт `POST /api/v1/auth/logout`
- [ ] Скрытие действий по роли (таблица в разделе 3), не только дизейблинг
- [ ] Раздел "Пользователи" в UI для `ADMIN` (создание/список/роль/enabled/сброс пароля)
- [ ] Убрано поле "от чьего имени запускать" из формы запуска сценария (раздел 5)
- [ ] Обработка новых кодов ошибок (раздел 6) — как минимум `INVALID_CREDENTIALS` на экране логина
