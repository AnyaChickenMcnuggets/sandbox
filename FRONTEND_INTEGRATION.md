# Инструкция для фронтенда: аутентификация, прогоны, отчёты (Sprint 26-32)

## Sprint 33: письмо по флагу запуска, комментарии в отчёте

### Галочка "прислать отчёт на почту"
```
GET /api/v1/report/settings            -> { "mailAvailable": true }   (любой залогиненный)
POST /api/v1/scenarios/{id}/run        { "startStepId": null, "sendReportByMail": true }
```
- Показывайте галочку только при `mailAvailable: true`. `sendReportByMail` необязательное,
  по умолчанию письмо **не** отправляется.
- Если отправить `sendReportByMail: true`, а на сервере отправка не включена - `400 INVALID_REQUEST`,
  прогон не создаётся (сообщение в `message`).
- Письмо уходит тому, под кем вы залогинены (логин + почтовый домен из настроек сервера), когда
  прогон завершён (успешно, с ошибкой или остановлен). В письме итог и, если на сервере задан адрес
  сервиса, ссылка на отчёт.

### Отчёт
Комментарии к шагам - тот же текст, что сохранён для шага, переведённый на русский ("Проверка очереди
«q» (попытка 2): всего 2 (Успешно: 1, Ошибка: 1)", "Задание «J» завершилось на роботе «r»: успешно"),
без потери подробностей. Для невыполненных шагов - причина ("прогон начат с середины сценария...",
"шаг «X» (№5), от которого он зависит, завершился с ошибкой"). Исходный английский текст - в
сворачиваемом блоке "Технические детали". В `?format=json` поля `detail` / `errorMessage` остаются
сырыми (английскими, для запусков до перевода логов - русскими): для своего вида берите их как
технические.

## Sprint 32: отчёт по прогону

### Открыть отчёт (право `RUN_READ`)
```
GET /api/v1/runs/{runId}/report            -> HTML-страница (по умолчанию)
GET /api/v1/runs/{runId}/report?format=json -> тот же отчёт данными
```
- HTML самодостаточный: стили и диаграмма внутри, скриптов нет. Открывайте его **ссылкой в новой
  вкладке** (`target="_blank"`, куки уходят сами, как с остальным API). В PDF - обычная печать
  браузера (Ctrl+P, "Сохранить как PDF"), под печать заданы стили. Встраивать в `<iframe>` нельзя
  (запрещено заголовками `X-Frame-Options` и `frame-ancestors 'none'`), как и вставлять через
  `innerHTML` (ответ идёт с `Content-Security-Policy: default-src 'none'`) - только отдельный документ.
- Что в отчёте: итог (УСПЕШНО / ЕСТЬ ОШИБКИ / ОСТАНОВЛЕН ПОЛЬЗОВАТЕЛЕМ), кто и когда запустил,
  длительность, диаграмма последовательности шагов (Sankey), таблица шагов, причина ошибки, проверки
  очередей (ожидалось / получено / не хватает) с транзакциями, задания (робот, времена), очереди.
- `409 CONFLICT` - прогон ещё выполняется: показывайте кнопку "Отчёт" только для прогонов в статусе
  `SUCCEEDED` / `FAILED` / `STOPPED` (`RunResponse.status`). `404` - нет такого прогона.
- Отчёт - **снимок на момент завершения**: он не меняется после `cleanup` и правок сценария.
  Для прогонов, завершившихся до этой версии, отчёт строится при первом открытии, без данных проверок
  (в нём так и написано).
- `?format=json` - если нужно нарисовать свой вид: `{runId, scenarioName, triggeredBy, status,
  startedAt, finishedAt, durationSeconds, steps[{id,name,type,status,durationSeconds,detail,
  errorMessage,result}], edges[{from,to}]}`. Поле `result` у шага зависит от типа (`JOB`: робот и
  задание; `QUEUE_CHECK`: `expected`, `actual`, `passed`, `transactions`) и может быть `null`.

### Письмо
Если на сервере включено (`report.notification.enabled`), тот, кто запустил прогон, получает письмо
о завершении (короткая справка и, если задан адрес сервиса, ссылка на отчёт). Со стороны фронта ничего
делать не нужно. Ссылка в письме ведёт на этот же эндпоинт, поэтому открывается только при входе в систему.

## Sprint 31: список прогонов `GET /api/v1/runs`, `triggeredBy` в ответе

### Список прогонов (право `RUN_READ`)
```
GET /api/v1/runs?scenarioId=5&page=0&size=20
```
- `scenarioId` — необязательный фильтр по сценарию. Неизвестный id — пустая страница, не `404`
  (история живёт и после удаления сценария).
- `page` с 0 (по умолчанию `0`), `size` от 1 до 100 (по умолчанию `20`). Иначе `400 INVALID_REQUEST`.
- Порядок: по `startedAt` от новых к старым; прогон, который ещё не начался (`startedAt: null`,
  статус `PENDING`), идёт первым — он самый новый. Одинаковые `startedAt` — по `id` по убыванию.
```json
{ "content": [
    { "id": 12, "scenarioId": 5, "scenarioName": "Сверка", "triggeredBy": "alice",
      "status": "SUCCEEDED", "startedAt": "...", "finishedAt": "...", "startStepId": null } ],
  "page": 0, "size": 20, "totalElements": 41, "totalPages": 3 }
```
Строка списка — без `steps` (шаги не грузятся на каждую строку). Детали прогона и шаги —
`GET /api/v1/runs/{id}` как раньше. `scenarioName` и `triggeredBy` есть прямо в строке: отдельный
запрос за именем сценария не нужен, видно кто запустил.

### `RunResponse` (`GET /api/v1/runs/{id}`, ответы запуска/остановки)
Добавилось поле `triggeredBy` — логин, под которым пользователь был залогинен в момент запуска
(сервер берёт его из аутентификации, не из запроса). `scenarioName` в ответе уже был.

## Sprint 29: права вместо ролей в UI, смена пароля, админ матрицы, таймауты шагов

### 1. UI-гейтинг — по `permissions`, не по `role` (ВАЖНО, меняет раздел 3 ниже)
Что может роль, теперь настраивает админ без деплоя, поэтому таблица ролей в разделе 3 — лишь
**стартовые значения**. `GET /api/v1/auth/me` теперь возвращает права текущей роли:
```json
{ "username": "alice", "role": "OPERATOR",
  "permissions": ["CLEANUP","ORCHESTRATOR_READ","RUN_READ","RUN_START","RUN_STOP","SCENARIO_READ","SCENARIO_WRITE"] }
```
Показывайте/скрывайте кнопки по наличию права: `SCENARIO_WRITE` — создать/править сценарий,
`SCENARIO_DELETE` — удалить, `RUN_START` — запуск, `RUN_STOP` — остановка, `CLEANUP` — очистка,
`RUN_READ`/`SCENARIO_READ`/`ORCHESTRATOR_READ` — просмотр, `USER_MANAGE` — раздел "Пользователи",
`ROLE_MANAGE` — раздел "Роли и права". Не завязывайтесь на имя роли (`role == "ADMIN"`): админ может
выдать права любой роли, а у роли без единого права `/me` всё равно вернёт `200` с пустым списком.
Перечитывайте `/me` при старте и после ответа `403` — права могли измениться.
Любой запрос к эндпоинту, права на который нет → `403 FORBIDDEN` (формат ошибки прежний).

### 2. Смена своего пароля
```
POST /api/v1/auth/change-password
{ "currentPassword": "...", "newPassword": "минимум 8 символов" }
```
Любой залогиненный пользователь. `200` + `{"expiresInSeconds":900}` и **новые куки** (как после
логина — ничего хранить не нужно, браузер заменит сам). Ошибки: `400` (`INVALID_REQUEST`) — текущий
пароль неверен или новый совпадает с текущим; `400` (`VALIDATION_FAILED`) — новый короче 8 символов;
`401` — нет сессии. Все остальные сессии этого пользователя (другие браузеры/устройства)
разлогиниваются. Не путать с админским сбросом пароля (`PUT /admin/users/{id}/password`) — там
текущий пароль не нужен.

### 3. Админка матрицы ролей и прав (право `ROLE_MANAGE`, по умолчанию только `ADMIN`)
```
GET /api/v1/admin/permissions
→ [ { "code": "SCENARIO_READ", "description": "Просмотр списка и деталей сценариев" }, ... ]

GET /api/v1/admin/roles
→ [ { "role": "ADMIN", "permissions": [...все...], "editable": false },
    { "role": "OPERATOR", "permissions": [...], "editable": true },
    { "role": "VIEWER", "permissions": [...], "editable": true } ]

PUT /api/v1/admin/roles/{role}/permissions
{ "permissions": ["SCENARIO_READ", "RUN_READ"] }
→ тот же объект роли после изменения
```
Рисуйте таблицу "право (строки) × роль (колонки)" с чекбоксами. Столбец `ADMIN` — только
отображение (`editable: false`, `PUT` для него даст `400`). `PUT` — **полная замена** набора роли
(шлите все выбранные права, не дельту), пустой список допустим. Изменение действует сразу, без
перелогина пользователей. Неизвестный код права/роли — `400`.

### 4. Таймауты шагов сценария — теперь только в конфиге шага, по умолчанию их нет
Раньше скрытые 30 минут (JOB) и 10 минут (QUEUE_CHECK) вшиты на бэкенде. Теперь глобальных
таймаутов нет: шаг ждёт без ограничения, пока автор сценария не задал свой. В редакторе сценария
добавьте **необязательные** поля (пусто = без таймаута, не слать `0`, а опускать поле/`null`):
- `JOB`: `timeoutSeconds` (макс. время ожидания завершения задания на роботе),
  `pollIntervalSeconds` (интервал опроса, по умолчанию 5 с) — `config` шага рядом с
  `rpaProjectId`/`rpaProjectName`/`arguments`;
- `QUEUE_CHECK`: `timeoutSeconds`, `pollIntervalSeconds` — уже были, но у `timeoutSeconds`
  больше нет дефолта в 10 минут.
В UI запуска стоит предупреждать, если в сценарии есть `JOB`/`QUEUE_CHECK` без `timeoutSeconds`:
такой прогон может идти бесконечно (остановить — `POST /api/v1/runs/{id}/stop`, право `RUN_STOP`).

**Чек-лист Sprint 29:** [ ] гейтинг по `permissions` из `/me`, не по `role` · [ ] форма смены
пароля · [ ] раздел "Роли и права" для `ROLE_MANAGE` · [ ] поля `timeoutSeconds`/
`pollIntervalSeconds` в редакторе шагов `JOB` и `QUEUE_CHECK` (необязательные)

## Что поменялось в Sprint 27 — читайте, если уже начали интеграцию по Sprint 26

**Токены больше не приходят в теле ответа и не хранятся на фронте вообще.** Раньше `/auth/login`
возвращал `{"accessToken":"...","refreshToken":"...",...}`, и инструкция просила сохранить их в
`localStorage`/`sessionStorage` и вручную слать `Authorization: Bearer`. Это оказалось дырой:
значение в `localStorage` читает (и может подменить) любой JS на странице, в том числе
подсунутый через XSS. Исправлено — токены теперь в `HttpOnly`-куках (`Set-Cookie`), недоступных
JS; тело `/auth/login`/`/auth/refresh` — только `{"expiresInSeconds": 900}`.

**Если фронт уже реализован по Sprint 26-инструкции — выкиньте весь код хранения/подстановки
токенов.** Браузер теперь делает это сам: при `fetch`/`XHR` с `credentials: "include"` кука
уходит автоматически, ничего вручную подставлять не нужно (и нечего — сырого значения токена
фронт больше не видит). Подробности — раздел 2 ниже, полностью переписан.

**Новое обязательное условие: фронт и backend должны быть на одном origin** (тот же домен+порт+
протокол) и backend — **за HTTPS в проде/стейджинге**. Кука с `SameSite=Strict` не уйдёт на другой
origin вообще, а `Secure`-куку браузер не отправит по `http://`. Если сейчас фронт и backend на
разных портах/доменах — скажите backend-команде, это отдельный разговор (CORS +
`SameSite=None` — другой набор компромиссов по CSRF, не мелкая правка).

**Не breaking для остального**: роли/матрица доступа (раздел 3), admin API (раздел 4),
`triggeredBy` (раздел 5) — без изменений относительно Sprint 26, инструкция ниже та же.

Техническое обоснование — `docs/adr/0003-own-api-authentication-jwt-rbac.md` (роли/механизм),
`docs/adr/0004-cookie-based-tokens-and-https.md` (куки/HTTPS), раздел "Аутентификация нашего API"
в `architecture.md`.

## 1. Что нужно сделать

1. Экран логина (username + password).
2. **Хранить токены не нужно** — браузер делает это через куки. Просто вызывайте `/auth/login` и
   дальше ничего руками не подставляйте.
3. Все запросы к API (кроме уже решённых браузером кук) должны идти **с `credentials: "include"`**
   (`fetch`) или `withCredentials: true` (`XMLHttpRequest`/axios) — иначе браузер не приложит куки.
4. Обработка истечения access-токена (15 минут) — `401` → один раз `/auth/refresh`, при неудаче —
   редирект на логин (детали — раздел 2).
5. Скрытие/дизейблинг элементов UI по роли пользователя (см. раздел 3).
6. Поле "кто запускает" в форме запуска сценария, если оно было — убрать, сервер его больше не
   принимает (раздел 5).
7. Убедиться, что dev-окружение фронта (например, `vite`/`webpack-dev-server`) либо проксирует API
   на тот же origin, либо backend поднят на `http://localhost` с `AUTH_COOKIES_SECURE=false` (см.
   `HTTPS_SETUP.md`) — иначе куки в dev не будут работать как в проде.

## 2. Поток аутентификации

### Логин

```
POST /api/v1/auth/login
Content-Type: application/json

{ "username": "operator1", "password": "..." }
```
Запрос должен идти с `credentials: "include"`, иначе браузер не сохранит куки из ответа.

Успех — `200`, тело:
```json
{ "expiresInSeconds": 900 }
```
Сами токены — в заголовках ответа (`Set-Cookie: access_token=...; HttpOnly; ...` и аналогично
`refresh_token`), браузер сохраняет их сам, фронту их не видно и не нужно их видеть.

Неверный логин/пароль или отключённый пользователь — `401`:
```json
{ "code": "INVALID_CREDENTIALS", "message": "Неверный логин или пароль", "details": [] }
```
Сообщение намеренно не различает "нет такого пользователя" и "неверный пароль" — не показывайте
пользователю более конкретную подсказку, чем пришла от сервера.

### Использование access-токена

Ничего делать не нужно — кука `access_token` уходит с каждым запросом на тот же origin
автоматически (если запрос сделан с `credentials: "include"`/`withCredentials: true`).
Просроченный/невалидный/отсутствующий токен → `401`, недостаточно прав для конкретного действия
(роль есть, но не та) → `403`. Оба варианта — тот же JSON-формат ошибки, что и остальной API
(`ErrorResponse`: `code`/`message`/`details`).

### Обновление токена (refresh)

```
POST /api/v1/auth/refresh
```
Без тела — refresh-токен сервер берёт из куки `refresh_token` сам (`credentials: "include"`
обязателен и здесь). Успех — `200`, `{"expiresInSeconds": 900}`, сервер уже поставил новую пару
кук (ротация — старый refresh-токен сразу становится недействителен, но это тоже невидимо фронту,
куки просто заменились). Невалидный/просроченный/отсутствующий refresh-токен → `401` — в этом
случае обычный сценарий фронтенда: разлогинить пользователя и показать экран логина заново, не
зацикливать retry.

Рекомендуемая логика: на каждый `401` от API (кроме самого `/auth/login`) — один раз попробовать
`/auth/refresh`, при успехе повторить исходный запрос (кука уже новая, просто повторите тот же
вызов); при неудаче — разлогин.

### Logout

```
POST /api/v1/auth/logout
```
Без тела (снова берёт refresh-токен из куки). `204 No Content`, сервер отзывает refresh-токен и
присылает `Set-Cookie` с истёкшим сроком на обе куки (браузер их удаляет). Зовите при явном выходе
пользователя.

## 3. Матрица ролей — что доступно

Три роли, у пользователя ровно одна. Если запрос успешен на бэке, но роли не хватает — `403`, не
`404`/пустой ответ, так что можно (и нужно) заранее скрывать недоступные действия в UI, а не только
ловить ошибку постфактум.

| Действие | VIEWER | OPERATOR | ADMIN |
|---|:---:|:---:|:---:|
| Смотреть список/детали сценариев | ✅ | ✅ | ✅ |
| Смотреть статус прогона, элементы очереди, доступность роботов | ✅ | ✅ | ✅ |
| Создать/отредактировать сценарий | ❌ | ✅ | ✅ |
| Запустить/остановить прогон, cleanup | ❌ | ✅ | ✅ |
| Удалить сценарий | ❌ | ❌ | ✅ |
| Управление пользователями (`/api/v1/admin/users/*`) | ❌ | ❌ | ✅ |

`VIEWER` — режим "только просмотр": прячьте кнопки создания/запуска/удаления целиком, не просто
дизейбльте — так понятнее, что это не баг. `ADMIN`-раздел (управление пользователями) — отдельный
пункт меню, видимый только `ADMIN`.

**Роль — через `GET /api/v1/auth/me`** (добавлен в Sprint 28, по вашему же вопросу). Токен в
`HttpOnly`-куке, декодировать JWT на фронте нельзя — этот эндпоинт и есть ответ:
```
GET /api/v1/auth/me
```
→ `200`:
```json
{ "username": "alice", "role": "OPERATOR" }
```
Без аутентификации (нет/просрочена кука) → `401`, как и у любого другого эндпоинта. Доступен
ЛЮБОЙ аутентифицированной роли, включая `VIEWER` — это "кто я", а не операция, требующая
конкретных прав. Зовите его сразу после успешного `/auth/login` (роль не приходит в ответе
`/auth/login` — он возвращает только `expiresInSeconds`, роль — отдельным запросом) и при
восстановлении сессии на старте приложения (есть кука с прошлого визита — `/me` подтвердит, что
она ещё действительна, и скажет, под какой ролью). `401` от `/me` при старте приложения — обычный
сигнал "показать экран логина", не ошибка.

## 4. Админ-панель: управление пользователями

Все — только с ролью `ADMIN`, все под `/api/v1/admin/users`. Все запросы — с `credentials:
"include"`, как и везде (раздел 1).

**Создать пользователя**
```
POST /api/v1/admin/users
{ "username": "operator1", "password": "минимум 8 символов", "role": "OPERATOR" }
```
→ `201`, тело — `UserResponse` (см. ниже). Дубликат `username` → `409 CONFLICT`. Короткий пароль
→ `400` (стандартная валидация, `code: "VALIDATION_FAILED"`).

**Список / один пользователь**
```
GET /api/v1/admin/users
GET /api/v1/admin/users/{id}
```
`UserResponse`:
```json
{ "id": 5, "username": "operator1", "role": "OPERATOR", "enabled": true, "createdAt": "2026-09-29T10:00:00+03:00" }
```
Пароля/хэша в ответе никогда нет.

**Сменить роль**
```
PUT /api/v1/admin/users/{id}/role
{ "role": "ADMIN" }
```

**Включить/отключить**
```
PUT /api/v1/admin/users/{id}/enabled
{ "enabled": false }
```
Отключение — не удаление, строка остаётся (аудит). Отключённый пользователь не может залогиниться,
и его уже выданные токены сразу перестают работать (не только будущий логин).

**Сбросить пароль**
```
PUT /api/v1/admin/users/{id}/password
{ "newPassword": "минимум 8 символов" }
```
→ `204`. Удаления пользователя нет — только `enabled: false`.

Первого `ADMIN` фронт не создаёт — он заводится backend'ом при первом старте (см. `TESTING.md`,
раздел "0a. Первый ADMIN и логин"), спросите его логин/пароль у бэкенд-команды/DevOps.

## 5. Breaking change: поле `triggeredBy` убрано из запроса запуска

Раньше:
```
POST /api/v1/scenarios/{id}/run
{ "triggeredBy": "имя_которое_вводил_пользователь", "startStepId": null }
```
Теперь `triggeredBy` в теле запроса **игнорируется/не принимается** — сервер сам берёт имя из
аутентификации. Если в форме запуска было поле "от чьего имени запускать" — уберите его, это
больше не нужно и не имеет эффекта. Тело запроса теперь:
```json
{ "startStepId": null }
```
(поле `startStepId` можно вообще не передавать, если запуск с начала — тело необязательно, как и
раньше). Поле `triggeredBy` в ответах `GET /api/v1/runs/{runId}` и `GET /api/v1/runs` появилось только в
Sprint 31 (раньше в ответ не попадало); значение — "кто реально был залогинен", не то, что
ввели в форму.

## 6. Формат ошибок (без изменений, для справки)

Все ошибки API — единый JSON:
```json
{ "code": "STRING_CODE", "message": "человекочитаемый текст", "details": [] }
```
Новые коды (с Sprint 26), которых раньше не было:

| HTTP | code | Когда |
|---|---|---|
| 401 | `UNAUTHORIZED` | нет токена / просрочен / подделан |
| 401 | `INVALID_CREDENTIALS` | неверный логин/пароль при `/auth/login`; невалидный refresh-токен при `/auth/refresh` |
| 403 | `FORBIDDEN` | токен валиден, но роли не хватает на это действие |
| 409 | `CONFLICT` | (уже было) — теперь также при создании пользователя с занятым `username` |

## 7. Информационно: `QUEUE_CHECK` теперь иногда падает быстрее (Sprint 27)

Не API-контракт, просто чтобы не удивляться в UI прогона: если шаг сценария типа `QUEUE_CHECK`
отслеживает конкретные транзакции (`naturalKeys`) и все они уже получили финальный статус, не
подходящий под ожидание (например, ожидали `SUCCESS`, а пришло `ERROR` без оставшихся повторов) —
шаг теперь падает заметно быстрее, не дожидаясь полного таймаута (который мог быть 10+ минут).
Сообщение об ошибке в `StepRunResponse.errorMessage`/`detail` в этом случае начинается с "все
отслеживаемые транзакции уже получили конечный статус" — если в UI есть специальная обработка
текста ошибки таймаута, этот текст теперь встречается тоже, просто раньше по времени.
